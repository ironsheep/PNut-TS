# Map File Verification Tests

## Purpose

Verify that `.map` files generated by the `-m` flag accurately reflect the
compiled object structure. `src/tests/MAP-tests/map.test.ts` compiles each
fixture below (staged into a private temp tree — nothing under `TEST/` is
ever written to) and cross-checks the result against three independent
sources:

1. **The `.map` file itself** — parsed by `mapParser.ts`, the one parser for
   the grammar specified in `DOCs/internals/MAP-File-Format.md`.
2. **`expected.json`** — facts a human can check directly against the
   `.spin2` source: instance paths, image membership, method/DAT/PASM-label
   names, VAR symbol names/types/sizes, and override strings. It never
   carries an address; every address comes from the map.
3. **`mapOracle.ts`** — an independent header-walk decoder of the `.lst`
   listing's hex dump, built from the interpreter's object-call rule, not
   from the compiler's own `ObjectLayout`/`mapGenerator`. Image bases read
   from the map are cross-checked against this decode.

This suite (`map.test.ts`) owns the eight named fixtures below and their exact
facts. `mapFormat.test.ts` (a separate suite) owns the format itself: the
spec's worked example byte for byte, warm-cache-equals-cold on every shape in
the shape matrix, and the named edge cases (PASM-only, no VAR, no DAT, a
255-element array, wide instance paths, a failed compile). Nothing here
duplicates that coverage.

## What `verify-map.ts` checks

For every fixture:

- **Image facts** (`checkImages`): image count; each image's `Source` cell;
  the exact set of method names in that image; each expected `DAT` name and
  type; each expected PASM label name.
- **Instance facts** (`checkInstances`): instance count; which image each
  instance runs (`#n`); the instance's `Overrides` cell; each expected VAR
  symbol's type and size, and that `address == instance VAR base + offset`
  (both numbers read from the map's own `MEMORY LAYOUT` and `OBJECT DETAILS`
  tables).
- **Method entries, exactly** (`checkMethodEntries`): for every row in every
  image's `Methods` sub-table, `absolute == image base + relative` — the
  offset and address are both read straight from the map text; the image
  base comes from `MEMORY LAYOUT`. This is the check that punch item 14a
  weakened to `mapEntry >= 4*(methods+1)` when the map still printed
  header-table slot indices in an address column; the map now prints real
  addresses, so the exact identity holds and is asserted.
- **DAT / PASM / Inline PASM entries** (`checkOtherOffsetRows`): the same
  `absolute == base + relative` identity for every other offset-bearing row.
- **Image bases against the independent decoder**
  (`checkImageBasesAgainstOracle`): each `MEMORY LAYOUT` image's `Range`
  start must equal the base mapOracle's header walk computes from the `.lst`
  hex dump, decoded without reference to the map or to `ObjectLayout`.

A `verify-map.ts` failure always names the symbol, method, DAT label, PASM
label or image involved — see `mapVerifyFalsification.test.ts` for proof the
checker can actually fail: a wrong `expected.json` entry is reported by name,
and a method `Address` corrupted by one long (`checkMethodEntries`) is
reported by method name, not silently accepted.

## The eight fixtures

### test1-simple — basic parent/child
One `OBJ` declaration, no overrides: 2 images, 2 instances. Exercises the
baseline `Methods`, `DAT` and `VAR` sub-tables and both indexes.

### test2-deep — three levels
`top -> MID -> MID.LEAF`: 3 images, 3 instances, one per level. Exercises
nested instance paths and `Child slots` two levels deep.

### test3-wide — one top, three siblings
`CHILDA` (DAT, no PASM), `CHILDB` (PASM labels under `ORG`, no DAT), `CHILDC`
(DAT, three methods including a `PRI`): 4 images, 4 instances. Exercises the
`PASM labels` sub-table and mixed VAR types (BYTE, WORD, LONG) across
siblings.

### test4-override — constant overrides that fork the image
Three instances of `param_child`, each overriding `DEFAULT_VALUE` (and one
also `MULTIPLIER`) — every override changes a compiled immediate, so all
three fork into separate images from the same source file: 4 images total.
This is the case that exposed two generator defects fixed in 1.55.4: every
symbol appearing once at the first image's base, and method rows carrying
header-table slot indices in the `Address` column. `map.test.ts` has an
extra `describe` block here checking `SYMBOL INDEX`, `ADDRESS INDEX` and
method placement directly against the raw map text, independent of
`verify-map.ts`.

### test5-inline — inline PASM inside a method
An `ORG` … `END` block inside `PUB runInline()`: exercises the `Inline PASM`
sub-table with a real `Cog` address (as opposed to `PASM labels`, which is
for `ORG` outside any method).

### test6-hubexec — hub-executable DAT (`ORGH`)
DAT-level `orgh` code: exercises DAT rows for what would be cog-mode PASM
labels in `test3-wide` — `ORGH` labels are hub-mode DAT, not `PASM labels`,
and have no cog address.

### test7-version — explicit language version
`{Spin2_v45}` at the top of the source: exercises the map header's
`Spin2_v<n>` line against `expected.json`'s `language_version`.

### test8-struct — STRUCT VAR symbols
Adapted from `TEST/LANG-FEAT-tests/struct_basic.spin2`: a `rect` STRUCT
nesting two `point` STRUCTs (`BOX`, type `STRUCT`, size 16 — two 8-byte
points) and an array member (`SAMPLES`, type `LONG`, size 12 — three longs).
Exercises `Type` values wider than `BYTE`/`WORD`/`LONG` and multi-element
`Size` totals in the `VAR` sub-table.

## expected.json schema

```json
{
  "description": "one-line description of what this fixture exercises",
  "top_file": "top.spin2",
  "language_version": 45,
  "images": [
    {
      "source": "top.spin2",
      "methods": ["methodName", "..."],
      "dat": [{ "name": "datName", "type": "LONG|WORD|BYTE|STRUCT" }],
      "pasm_labels": ["labelName"]
    }
  ],
  "instances": [
    {
      "path": "(top)",
      "image": 0,
      "overrides": "-",
      "vars": [{ "name": "varName", "type": "LONG|WORD|BYTE|STRUCT|^LONG|^WORD|^BYTE|^STRUCT", "size": 4 }]
    }
  ],
  "totals": {
    "instance_count": 1,
    "image_count": 1
  }
}
```

- `images[i]` corresponds to map image `#(i+1)`; fixtures are written so the
  images are already listed in ascending-address order.
- `instances[].image` is the 0-based index into `images`.
- `overrides` is the raw `Overrides` cell (`-` when omitted) — the same text
  the map prints, in declaration order.
- `vars[].size` is the symbol's total byte size (element size × element
  count), matching the map's `Size` column exactly — never an element count.
- No field in this file is an address. Every address is read from the map at
  verification time and cross-checked against `mapOracle`.

## Running the tests

```bash
npm run test-map
# or, to force --runInBand:
npm run build && jest --runInBand -c jest-config/jest-map-only-config.json
```

Never run the full smm suite alongside another jest process.

## Files

- `README.md` — this document
- `mapParser.ts` — the shared parser for the `.map` grammar (used by
  `verify-map.ts`; independent of `src/classes`)
- `verify-map.ts` — `expected.json`-driven checks plus the pure, unit-testable
  `checkMethodEntries` / `checkOtherOffsetRows` / `checkImageBasesAgainstOracle`
  helpers
- `mapOracle.ts` — the independent header-walk decoder (shared with
  `mapFormat.test.ts` and the shape-matrix suites)
- `map.test.ts` — this suite: the eight named fixtures
- `mapVerifyFalsification.test.ts` — proof the checkers above can fail, and
  name what's wrong when they do
- `mapFormat.test.ts`, `shapeMatrix.ts`, `mapOracleShapes.test.ts`,
  `mapOracleGold.test.ts`, `mapOracle.test.ts`, `objectLayout.test.ts` — the
  format-level and oracle-level suites (not fixture-specific; see their own
  headers)
- `test1-simple/` … `test8-struct/` — the eight fixtures, each a `.spin2`
  source (or several, for the multi-object fixtures) plus `expected.json`
- `spec-example/`, `shapes/` — fixtures owned by `mapFormat.test.ts`, not by
  this suite
